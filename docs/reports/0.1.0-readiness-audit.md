## Performance Research

### Workload

0.1.0 readiness workloads:

- Developer verification: lint, typecheck, package tests, build.
- Web build output: client/server bundle size.
- UI generated-output verification: fixture app typecheck/build.

### Budget

Practical provisional budget for 0.1.0:

- Full local verification under 15 seconds on this machine.
- Web client main JS under 200 kB raw and 70 kB gzip.
- No test suite over 10 seconds.
- No known avoidable Vite/Turbo configuration bottleneck.

### Baseline

Current verification is inside budget. The slowest test workload is Mason CLI at 4.65 s because it typechecks/builds a generated fixture app, which is intentional for release safety.

### Bottleneck Evidence

No measured performance bottleneck currently blocks 0.1.0. The only performance-adjacent risks are configuration and future growth:

- Root `bun run build` only builds the docs app because only `docs` has a `build` script.
- Root `check-types` only runs packages that define `check-types`.
- Web app main client bundle is 146.45 kB raw / 48.06 kB gzip, acceptable for a placeholder app but should get a budget before docs/demo growth.
- Vite guidance warns that barrel files and broad import surfaces can hurt dev-page load and transform work as projects grow. Core currently has broad public `index.ts` / `utils` surfaces.
- Turborepo docs note outputs affect caching. Test tasks currently set `outputs: []`, which is fine for non-artifact tests; build outputs are `dist/**`.

### Research Notes

- Vite's official performance guide recommends measuring with profiling/debug tools, auditing plugins, avoiding unnecessary resolve work, and avoiding barrel files when they force more files to load/transform.
- Turborepo's configuration docs state task `outputs` control what gets cached and that empty outputs mean no artifact caching except logs.

## Architecture Improvement Candidates

1. **Core Kernel Public Surface**

Files:

- `packages/core/src/index.ts`
- `packages/core/src/utils/index.ts`
- `packages/core/src/overlay/index.tsx`
- `packages/core/package.json`

Problem:

The current public interface exposes broad kernel modules as `./utils` and `./overlay`. That creates a shallow module shape: callers must understand which pieces are stable public API and which are primitive support internals.

Solution:

Decide the 0.1.0 public interface deliberately. Keep only stable primitive and intentionally public utility interfaces exported; move implementation-heavy internals behind private module paths or mark the package as preview-only.

Benefits:

- Locality: kernel changes can stay inside Keystone without breaking users.
- Leverage: primitive authors still get deep modules, but app users get a small stable API.
- Tests improve because the interface under test is the public primitive behavior, not incidental helper exports.

2. **Mason Registry Resolution Module Depth**

Files:

- `packages/mason-cli/src/install/plan.ts`
- `packages/mason-registry/src/resolve-dependencies.ts`
- `packages/mason-registry/src/validate-item.ts`
- `packages/mason-registry/src/validate-files.ts`

Problem:

Mason CLI resolves local registry items itself while Mason Registry has dependency and validation modules. The seam is split: validation depth lives in the registry package, but install resolution depth partly lives in the CLI.

Solution:

Move registry item loading/resolution semantics toward a deeper Mason Registry interface. The CLI should ask for an installable resolved graph and focus on project detection, target planning, and writes.

Benefits:

- Locality: registry format changes stay in Mason Registry.
- Leverage: CLI and future registry builders/docs can reuse one resolution module.
- Tests improve by separating registry graph behavior from filesystem write planning.

3. **UI Install Plan And Write Separation**

Files:

- `packages/mason-cli/src/install/plan.ts`
- `packages/mason-cli/src/install/write.ts`
- `packages/mason-cli/src/install/paths.ts`

Problem:

The write plan already has useful depth, but it mixes source content reading, target derivation, overwrite policy, dependency collection, and installed-item records. As registry item types grow, this module will become a broad coordination point.

Solution:

Split the install plan into smaller deep modules by concept: resolved item graph, target plan, dependency plan, and write application. Keep the CLI command as orchestration only.

Benefits:

- Locality: path/overwrite bugs stay in target planning.
- Leverage: dry-run, actual writes, and future diff/update can share the same install plan.
- Tests improve because dry-run and write behavior can assert the same plan object.

4. **Docs Product Surface Decision**

Files:

- `apps/docs/**`
- deleted `apps/fumadocs/**`
- `docs/**`

Problem:

Docs are currently durable Markdown artifacts, while the previous Fumadocs app is deleted. The repo has no settled docs product surface for examples, component pages, or registry previews.

Solution:

Choose one 0.1.0 docs module: restore/rebuild Fumadocs, use `apps/docs` as a docs/playground app, or explicitly defer public docs UI and keep Markdown-only docs for 0.1.0.

Benefits:

- Locality: docs work has one home.
- Leverage: examples, registry previews, and accessibility notes can share one surface.
- Tests improve because docs build/smoke checks can target one app.

5. **Core Form Control Naming**

Files:

- `packages/core/src/form/index.tsx`
- `packages/core/src/index.ts`

Problem:

`createFormControlTracer` and `FormControlTracer` leak milestone language into package API. The module is useful, but the interface name is stale.

Solution:

Remove the tracer aliases or move them to tests/docs only.

Benefits:

- Locality: implementation milestone language does not become API.
- Leverage: consumers see the durable concept, `createFormControl`.
- Tests remain unchanged if they use the real module interface.
